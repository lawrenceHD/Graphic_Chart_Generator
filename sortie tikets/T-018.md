- SEC-11 : clé d'objet générée par le serveur ; URL PUT de 5 min dont la signature couvre `content-length` ;
  `complete` vérifie l'existence et la taille de l'objet ; l'asset passe `quarantined`.
- SEC-12 : le type annoncé n'est pas lu.
- SEC-16 / ADR-023 : `content` répond `302` (`Cache-Control: no-store`, `X-Content-Type-Options: nosniff`) vers une
  URL de lecture de 5 min qui impose le type et la disposition ; `404` pour un original, un asset non `clean` ou un
  asset étranger.
- `can()` : `asset:create` sur le projet, puis sur le projet de l'asset ; un asset absent répond comme un asset
  étranger (`404`).

## Partie 2 — `asset.scan`
- Seul un asset `quarantined` est traité : le job est rejouable sans effet.
- Lecture plafonnée à 10 Mo. Type déterminé par les octets magiques. SVG limité à 5 Mo, assaini par liste blanche,
  `viewBox` complété par le rasteriseur isolé. Raster normalisé en PNG (sharp, `limitInputPixels`).
- Copie assainie sous une clé déterministe `…/sanitized` : une reprise écrase l'objet au lieu de laisser des
  orphelins.
- Une transaction fait passer l'original `clean` (`sha256`, type réel) et crée l'asset `logo_sanitized`.
- En cas de rejet : `rejected` + code stable, aucune copie.
- Tests (5) :
  - SVG nettoyé : copie différente de l'envoi, octets = sortie de `sanitizeSvg`, lignes et méta ;
  - idempotence, et asset `pending` ou absent ignoré ;
  - 4 rejets : script, type inconnu, SVG de plus de 5 Mo, objet disparu ;
  - PNG normalisé avec ses dimensions ;
  - journal masqué.
- Sabotage : copie stockée = octets d'origine → d'abord **non détecté**, car le SVG de test sortait identique de
  l'assainisseur. Test renforcé (commentaire et `metadata` à supprimer, copie différente de l'envoi) → 1 échec.
